## 2. 개요

의뢰 수주가 목적인 1인 디자이너 블로그에서, 의뢰가 정보가 빠진 채 접수되고 운영자가 이를 수작업으로 정리하느라 첫 답장이 늦어져 의뢰자가 이탈한다. **AI가 제출 전 의뢰자에게 빠진 정보를 안내하고, 제출 후 운영자에게 요약·적합도·답장 초안을 만들어** 첫 답장을 24시간 안에 보내게 한다.

## 3. 문제

### 3.1 데스크리서치

**3.1.1 SWOT**

| 강점 (S) | 약점 (W) |
|---|---|
| 디자인과 구현을 모두 함, 블로그·포트폴리오·의뢰 폼이 한 사이트, 4단계 의뢰 프로세스 명시 | 1인 운영으로 응답 리소스 한정, 트래픽 적음, 작업물·예산 구간이 플레이스홀더 |
| **기회 (O)** | **위협 (T)** |
| 수수료 없는 직접 의뢰 채널, AI로 1인 운영 효율화 | 외주 플랫폼 대비 낮은 신뢰, 응답이 늦으면 다른 디자이너로 이탈 |

**3.1.2 3C**: (Customer) 소상공인·스타트업은 디자인 용어에 익숙하지 않아 요구사항을 스스로 정리하기 어렵다. (Competitor) 외주 플랫폼은 정형화된 요청서와 응답 속도 표시로 신뢰를 준다. (Company) 개인 사이트는 둘 다 없으므로 정리 품질과 응답 속도로 차별화해야 한다.

### 3.2 문제 발굴

| # | 관점 | 문제 | 솔루션 방향 |
|---|---|---|---|
| U1 | 사용자 | 무엇을 적어야 할지 몰라 의뢰서가 불완전하다 | 제출 전 AI 누락 점검 |
| U2 | 사용자 | 비용 감이 없어 문의를 망설인다 | 예상 범위 안내 |
| U3 | 사용자 | 제출 후 진행 상황을 몰라 불안하다 | 제출 직후 요약·다음 단계 표시 |
| A1 | 관리자 | 의뢰를 읽고 정리해 답장 쓰는 데 시간이 걸린다 | AI 요약·답장 초안 |
| A2 | 관리자 | 맞지 않는 의뢰(예산·분야·스팸)에도 같은 시간을 쓴다 | AI 적합도 판별 |

### 3.3 문제 검증

- **3.3.1 계획**: 11/24 오전, 프리랜서 2~3명·디자인 외주 의뢰 경험자 2~3명 5분 인터뷰. "의뢰서 쓸 때 막막했던 점", "첫 답장까지 가장 오래 걸리는 일"
- **3.3.2 결과 및 인사이트**: [인터뷰 후 기입]

### 3.4 문제 최종 정의

**3.4.1 우선순위 (MoSCoW)**: U1·A1·A2는 Must. 같은 의뢰 데이터의 앞뒤라 한 흐름으로 구현·검증 가능하다. U3은 Should(U1과 같은 분석 결과 재사용). U2는 Could(가격 정책 확정 필요), 작업물 추천·글 요약·성과 리포트는 작업물과 트래픽이 부족해 2일 내 효과 검증이 어려워 제외.

**3.4.2 최종 정의**
> 의뢰가 불완전한 상태로 들어오고 그 정리를 운영자가 수작업으로 하느라 첫 답장이 늦어져, 의뢰자가 견적 단계 전에 이탈한다.

## 4. 해결 방안

### 4.1 솔루션 정의

하나의 AI 분석 함수가 의뢰의 **입구(제출 전 점검)와 출구(관리자 정리)** 를 모두 처리해, 의뢰자는 한 번에 완결된 의뢰를 보내고 운영자는 판단과 승인만 한다.

### 4.2 AS-IS / TO-BE

| 구분 | AS-IS | TO-BE |
|---|---|---|
| 컨셉 | 폼 접수 후 운영자가 전부 수작업 | AI가 점검·정리하고 사람이 승인 |
| 타겟 | 의뢰자·운영자 공통 불편 | 의뢰자: 작성 부담 감소 / 운영자: 처리 시간 단축 |
| 비즈니스 모델 | 의뢰 수주가 수익원 | 동일. 기능은 무료, 운영비는 건당 LLM API 비용(측정 예정) |
| 기능 | 자유 서술 폼 | 제출 전 누락 안내 + 관리자 요약·적합도·답장 초안 |
| 디자인 | 운영자가 원문을 직접 읽음 | 폼 하단 제안형 안내 / 관리자 카드(요약 → 누락 → 초안) |

### 4.3 예상 성과 (OKR)

- **O**: 의뢰자가 빠르고 정확한 첫 답장을 받아 견적 단계로 넘어가게 한다.
- **KR1**: 첫 답장 소요 시간 중앙값 24시간 이내 (출시 후 4주)
- **KR2**: 필수 4항목(일정·예산·범위·레퍼런스)을 갖춘 의뢰 비율 70% 이상
- **KR3**: 폼 시작 대비 제출 전환율, 출시 후 2주 기준선 측정 후 목표 확정

## 5. 가설 및 지표

### 5.1 핵심 지표

| 가설 | 지표 | 측정 | 목표 |
|---|---|---|---|
| H1. 제출 전 점검이 누락을 줄인다 | 필수 4항목 충족률 (점검 전 vs 후) | 테스트셋·제출 데이터 | 70% 이상 |
| H2. AI 정리가 처리 시간을 줄인다 | 건당 처리 시간 (수동 vs AI) | 테스트셋 15건 시간 측정 | 50% 단축 |
| H3. AI 판단은 신뢰할 만하다 | 누락 탐지율 / 적합도·스팸 판별 정확도 | 테스트셋 정답 비교 | 85% / 90% 이상 |

GA4 이벤트: `form_start` · `ai_check_shown` · `ai_check_fixed` · `form_submit`

### 5.2 고객 정의

- **1순위 고객 (의뢰자)**: 브랜드·상세페이지가 필요하지만 무엇을 요청할지 정리하기 어려운 소상공인·스타트업 마케터
- **운영자**: 작업과 의뢰 응대를 혼자 병행하는 1인 디자이너

### 5.3 마케팅 메시지

- 핵심 카피: "디자인 용어 몰라도 괜찮아요. 정리는 함께 할게요." / "24시간 안에 첫 답장을 드려요"
- 가이드: AI 안내는 지적이 아닌 제안형("~도 적어주시면 더 빨리 답드려요"), 확정 전 금액은 '예상 범위'로 표기
- 채널: 메인 카피 교체, 인스타그램·비핸스 프로필 링크

## 6. 기능적 요구사항

| ID | 기능 | 관점 | 설명 | 우선순위 |
|---|---|---|---|---|
| F1 | AI 분석 함수 | 공통 | 의뢰 텍스트 → 누락 항목·요약·분야·적합도·스팸 여부 JSON | Must |
| F2 | 제출 전 점검 | 사용자 | 제출 시 1회 점검, 누락 항목 제안형 안내 후 수정 또는 그대로 제출 | Must |
| F3 | 의뢰 저장 | 공통 | AI 성공 여부와 무관하게 즉시 저장 | Must |
| F4 | 관리자 의뢰 카드 | 관리자 | 요약·적합도·누락 항목 표시, 상태(신규/검토중/답장완료) 관리 | Must |
| F5 | 답장 초안 | 관리자 | 누락 항목 질문을 포함한 첫 답장 초안, 수정·복사 | Must |
| F6 | 실패 대체 경로 | 공통 | AI 실패 시 점검 생략 후 제출 허용, 관리자에 원문 표시·재시도 | Must |
| F7 | 제출 후 요약 화면 | 사용자 | 정리된 의뢰 요약, 다음 단계, 예상 답장 시점 | Should |
| F8 | GA4 퍼널 이벤트 | 공통 | 5.1 이벤트 4종 | Should |

**유즈케이스**: 의뢰자 폼 작성 → 제출 클릭 → F1·F2 누락 안내 → 보완 후 제출 → F3 저장 → (F7 요약) → 운영자 F4 확인 → F5 초안 수정 → 본인 메일로 발송 → '답장완료'
**범위 밖**: 대화형 챗봇, 메일 자동 발송, 견적 금액 자동 산정, 결제

## 7. 비기능적 요구사항

- 성능: 제출 전 점검 5초 이내(초과 시 F6), 관리자 분석은 비동기
- 보안: API 키는 서버 환경변수에만(클라이언트·GitHub 노출 금지), 관리자 페이지 로그인 필수
- 개인정보: LLM에는 의뢰 내용만 전달, 이름·이메일 미전달
- 안정성·비용: AI 장애가 의뢰 접수를 막지 않음, 입력 길이 제한으로 건당 비용 상한

## 8. 디자인 요구사항

- 기존 사이트 톤·컴포넌트 유지, AI 생성 영역에 'AI 초안' 배지로 검토 대상임을 표시
- 사용자 안내는 폼 흐름을 끊지 않는 인라인 카드, 관리자 카드는 판단 순서(요약 → 누락 → 초안) 배치
- 프로토타입: 배포 URL (1. 기본 정보)
