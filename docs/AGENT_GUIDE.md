# AGENT_GUIDE — 에이전트용 작업 지침

## 프로젝트 맥락

- 대상: 1인 디자이너의 포트폴리오 겸 블로그 (https://blog---261117.web.app), 비즈니스 목적은 디자인 의뢰 수주
- 해결할 문제: 의뢰가 정보가 빠진 채 접수되고 운영자가 수작업으로 정리하느라 첫 답장이 늦어져 의뢰자가 이탈한다
- 해결 방식: AI가 제출 전 의뢰자에게 누락 정보를 안내하고, 제출 후 운영자에게 요약·적합도·답장 초안을 제공한다
- 기준 문서: `docs/PRD.md` (범위와 우선순위는 이 문서를 따른다)
- **2026-11-24 PRD v0.3으로 전환**: AI 케이스 스터디 작성기. 아래 'F1~F8' 규격은 v0.2 의뢰 기능(이미 구현, 유지) 기준이며, v0.3 기능 번호와 다르다. 새 작업은 PRD v0.3 순서(F2 → F1 → F3 → F4 → F5 → F6 → F7)를 따른다
- 마감: 2026-11-25 16:50 (이후 커밋 불인정). 15:30 이후에는 기능 추가 금지, 문서와 버그 수정만

## 구현 범위와 순서

1. F1 AI 분석 함수 → 2. F3 의뢰 저장 → 3. F4 관리자 의뢰 카드 → 4. F5 답장 초안 → 5. F6 실패 대체 경로 → 6. F2 제출 전 점검 → (여유 시) F7 제출 후 요약, F8 GA4 이벤트
- 범위 밖: 대화형 챗봇, 메일 자동 발송, 견적 금액 자동 산정, 결제
- 범위 밖 작업이 필요해 보이면 구현하지 말고 사용자에게 먼저 묻는다

## v0.2 의뢰 기능: AI 분석 함수 규격 (옛 번호 F1, 유지)

- 입력: 의뢰 분야, 예산 선택값, 프로젝트 내용 (이름·이메일은 전달하지 않는다)
- `mode: "check"` (제출 전, 5초 이내 목표): `missing`만 반환
- `mode: "full"` (관리자용): 아래 전체 반환
- 출력은 JSON만, 설명이나 코드 블록 없이:

```json
{
  "missing": ["schedule", "budget", "scope", "reference"],
  "summary": "3줄 이내 요약",
  "category": "branding | uiux | content | other",
  "fit": "high | medium | low",
  "fit_reason": "한 줄",
  "is_spam": false,
  "reply_draft": "누락 항목에 대한 질문을 포함한 첫 답장 초안"
}
```

- 파싱 실패, 타임아웃, API 오류는 모두 F6 경로로 처리한다 (의뢰 저장은 절대 막지 않는다)

## 프롬프트 원칙

- 의뢰자 안내 문장은 지적이 아닌 제안형: "~도 적어주시면 더 빨리 답드릴 수 있어요"
- 확정되지 않은 금액은 '견적'이 아니라 '예상 범위'로 표현하고, 금액을 단정하지 않는다
- 답장 초안은 정중하고 짧게, 운영자가 수정할 것을 전제로 작성한다
- 프롬프트를 바꾸면 이유와 결과를 `docs/SUCCESS_FAILURE_LOG.md`에 남기고 `prompt:` 커밋으로 올린다

## 보안 규칙

- API 키는 서버 환경변수에만 둔다. 클라이언트 코드, 로그, 커밋에 절대 포함하지 않는다
- `.env`, 서비스 계정 키 파일은 `.gitignore`에 있어야 하며, 커밋 전 `git status`로 확인한다
- 관리자 화면과 관리자용 API는 로그인 없이 접근할 수 없어야 한다

## 커밋 규칙

- 기능 하나를 완성하고 동작을 확인할 때마다 커밋하고 바로 push 한다
- 메시지 접두어: `docs:` 문서 / `feat:` 기능 / `fix:` 버그 / `test:` 테스트 / `prompt:` 프롬프트 개선 / `chore:` 설정
- 메시지는 한국어로 무엇을 왜 바꿨는지 한 줄로 쓴다. 예: `feat: F4 관리자 의뢰 카드 - 요약·적합도·누락 항목 표시`
- 여러 기능을 한 커밋에 몰아넣지 않는다

## 기록 규칙

- 설계를 바꾸는 결정: `docs/DECISION_LOG.md`에 (날짜, 결정, 대안, 이유, 상태) 추가
- 테스트 실행과 실패: `docs/SUCCESS_FAILURE_LOG.md`에 (날짜, 대상, 결과, 실패 원인, 조치) 추가
- 테스트셋: `testset/requests.json`의 각 의뢰와 정답을 기준으로 정확도를 계산한다
- 화면 스크린샷: `docs/screenshots/`에 플로우 순서대로 번호를 붙여 저장한다

## PRD v1.1 F5 AI 케이스 스터디 초안 규격 (`generateCaseStudy`, 관리자 전용)

- 입력: 작업명(필수) · 분야 · 업종 · 기간 · 클라이언트(공개 동의 `clientPublic: true`일 때만 AI에 전달) · 메모 `{ request, work, result }` (한 칸 이상, 각 1500자 이하)
- 출력: `{ title, summary, problem, process, result, tags[] }` JSON 스키마 강제
- 메모에 없는 숫자가 초안에 있으면 `warnings.unsupportedNumbers`로 표시해 운영자가 게시 전에 확인 (H2)
- 실패(타임아웃 25초 · 파싱 · 거절 · API 오류)는 `{ ok: false, reason }` → 화면은 빈 템플릿으로 직접 작성 (F6 직접 쓰기)
- 프롬프트: `functions/casestudy-prompt.js` (메모에 있는 사실만, 수치·성과 생성 금지, 과장 수식어 금지)

## PRD v1.1 F7 인스타그램 문구 규격 (`generateSnsCopy`, 관리자 전용, 프롬프트 sns-v2)

- 입력: 운영자가 검토한 케이스 스터디(제목 · 요약 · 문제 · 과정 · 결과 · 분야 · 업종 · 태그, 클라이언트는 공개 동의 시만). 메모는 쓰지 않는다
- 출력: `{ captions[3], hashtags[] }` — 프로토타입 기준. 문구 3안, 각 3~4줄, 이모지 2~4개는 줄 맨 앞, 마지막 줄 "👉 과정은 프로필 링크에서", 3안은 말투와 시작을 다르게, 문구 안에는 해시태그를 넣지 않고 해시태그 3~5개는 따로
- 케이스 스터디에 없는 숫자는 `warnings.unsupportedNumbers`로 경고, 과장 금지
- 화면: '다른 문구 보기'로 3안을 돌려 보고, 고친 안을 골라 복사. 저장은 관리자 문서 `workNotes.sns`(captions · caption · hashtags · copiedAt)
- 채널은 인스타그램만 (DECISION_LOG D18)

## 기능 번호 대응표 (PRD v1.1에서 번호를 다시 매김)

| PRD v1.1 | 기능 | 예전 번호 (PRD v0.5~v1.0) |
|---|---|---|
| F1 | 한 줄 의뢰 (홈) | 없음 (새 기능) |
| F2 | 의뢰서 (레퍼런스 작업 고르기, 사진, 링크) | 없음 (새 기능) |
| F3 | 작업 목록 · 상세 · 의뢰 버튼 · 다른 프로젝트 | F4, F5 |
| F4 | 작업 입력 (정보, 이미지, 메모 3칸) | F1 |
| F5 | AI 케이스 스터디 초안 (보충할 점 안내) | F2 |
| F6 | 미리보기와 게시, 실패 시 직접 쓰기 | F3, F7 |
| F7 | 인스타그램 문구 3안 | F6 |

v0.2 의뢰 기능(AI 분석 · 의뢰 저장 · 관리자 의뢰 카드)은 이 번호와 별개로 "v0.2 의뢰 기능"이라고 부른다. 의사결정 로그 · 성공 실패 로그 · 작업 일지의 지난 기록은 당시 번호를 그대로 둔다.

## AI 비용 0원 운영 (D27)

- AI 초안과 인스타그램 문구는 `prototype.html`을 Claude 아티팩트로 열어 만든다 (`window.claude.use`, 운영자의 Claude 요금제 안). 결과를 사이트 작업 편집 화면에 붙여 넣고 게시한다
- AI를 쓸 수 없을 때는 문장 틀 초안(메모를 정해진 문장에 넣음)이나 직접 쓰기로 게시한다
- 서버 함수(`generateCaseStudy` · `generateSnsCopy`)는 코드와 테스트를 유지하되 배포는 선택이다. 배포하면 API 비용이 생긴다
- GA4 이벤트(F8)는 범위에서 뺐다 (D28)
